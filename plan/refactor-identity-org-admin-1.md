# Introduction

![Status: Planned](https://img.shields.io/badge/status-Planned-blue)

Refactor Event OS Admin to create users and capability-based organizations, collect and review organization KYB, manage capability-scoped organization memberships, and administer organization-owned vendor profiles and venues plus event-owned vendor callouts. Identity, Vendors, Venues, and Events remain the owners of their data and authorization rules; the admin UI uses gateway APIs only.

## 1. Requirements & Constraints

- **REQ-001**: Create a user through `POST /api/admin/users`; retain the returned UUID and use it as the organization owner ID.
- **REQ-002**: Create organizations through the existing admin gateway route backed by Identity `OrgService.CreateOrg`. Send one or more `organize`, `vend`, and/or `host` capabilities. Do not send the legacy `type` field.
- **REQ-003**: Submit organization KYB per capability using an admin-authorized Identity operation. Keep this separate from consumer `SubmitCapabilityKYB`, which requires a consumer session and organization membership. Persist only references to securely stored KYB artifacts, and audit the admin actor.
- **REQ-004**: Review capability KYB through `admin.kyb.review`; persist decision reason and actor. Expose review state in organization detail.
- **REQ-005**: A user may hold one organization membership and scoped role per capability scope. Resolve effective permissions for the selected scope and enforce capability status and permission checks in Identity, not only in the UI.
- **REQ-006**: Support organization member list, phone invite, invite list/revoke, scoped role and status changes, and removal. Do not expose direct add in this admin workflow; onboard new members through invitation. Do not allow changing/removing the organization owner.
- **REQ-007**: Vendor profiles support multiple profiles per managing organization. Organization is the ownership key; an account may be retained as a contact/provenance field, not as a uniqueness constraint that blocks sibling profiles.
- **REQ-008**: Organization-managed venues are distinct from global unclaimed directory venues and individually account-owned venues. Keep managing organization explicit through create, read, update, list, and archive/status operations; archive instead of physically deleting referenced venues.
- **REQ-009**: A vendor callout is owned by an event whose organization is selected in the admin UI. Support create/read/update while open and close/cancel lifecycle actions. Allow edits only before the first vendor response; after responses exist, close/cancel and create a replacement instead of changing the offer vendors already saw. Cancel is the auditable terminal equivalent of delete; never hard-delete callouts.
- **REQ-010**: Replace all admin organization `type` filters with capability filters. Map UI concepts explicitly: `organizer`→`organize`, `vendor`→`vend`, `venue`→`host`.
- **REQ-011**: Preserve UUID identifiers as strings in TypeScript, JSON, and protobuf. Remove legacy routes and fields outright; no compatibility aliases.
- **REQ-012**: Every workflow screen handles loading, error, empty, no-results, validation, and partial-success states; normalize nullable response arrays and invalidate affected TanStack Query caches after mutations.
- **REQ-013**: Allow an authorized admin to add a capability to an existing organization. A newly added capability starts pending KYB and must not grant active permissions until required KYB and activation decisions are complete.
- **REQ-014**: Manage each vendor profile's regional `ServiceArea` rows independently and show `ProfileStats` as server-derived, read-only aggregates. A profile may have multiple service areas; stats are not editable by admins.
- **SEC-001**: Do not put credentials, tokens, KYB PII, or KYB artifact references in source, plan files, snapshots, traces, console logs, or screenshots.
- **SEC-002**: Never impersonate the newly created user or bypass the gateway. Admin-assisted KYB and member operations use explicit admin-authorized Identity operations and auditable actor identity.
- **SEC-003**: Never accept arbitrary document URLs from a browser form as KYB evidence. Use an approved Documents artifact upload/reference flow and validate the artifact belongs to the organization/capability submission.
- **CON-001**: Admin repository root is `/Users/felixcoker/Documents/workspace/event-os/event-os-admin`; application source is `src/`, despite stale README text referring to `app/src/`.
- **CON-002**: Do not repurpose global directory, account-owned profile, or organizer self-service routes as organization-admin CRUD without preserving their ownership and authorization semantics.
- **CON-003**: Keep service-owned persistence and authorization inside Identity, Vendors, Venues, and Events; the gateway must not write service databases.
- **CON-004**: This is a hard-cutover refactor on a clean database. Do not plan or build backfills, compatibility aliases, deprecated fields, dual-read/write paths, or feature flags for the old model.
- **CON-005**: Verified Identity baseline (backend, 2026-11-02): RPCs `SetOrgCapabilityStatus`, `DecideCapabilityKYB`, `SubmitCapabilityKYB`, `GetOrgCapabilityState`, `TransferOrgOwner`, and member/invite RPCs already exist. `CreateOrg` creates one owner membership, for `capabilities[0]`'s scope only. `organization_members` is keyed `(org_id,user_id)` with `role_id` and no scope column; pending invites are unique on `(org_id,destination)`. `capability_kyb_evidence` and `KYBDocumentInput` store a raw `ref_url`. Permissions `admin.kyb.review`, `admin.kyc.review`, `admin.users.manage` (already covers org and vendor-profile creation), `admin.callouts.read|manage`, and `admin.events.manage` exist; `admin.kyb.submit` and any vendor/venue management permission do not.
- **CON-006**: Verified Vendors baseline: multiple profiles per org and the `managing_org_id` index already exist (migration 00015); status `deactivated` exists; service areas exist (migration 00016, `ListMy/ReplaceMyVendorServiceAreas`); admin routes `POST /api/admin/vendors`, `GET /api/admin/vendors[/{id}]`, and `PATCH /api/admin/vendors/{id}/status|tier` exist. No `ProfileStats` message exists; the vendor record carries only `rating` and `rating_count`.
- **CON-007**: Verified Venues baseline: `managing_org_id` and its index exist (migration 00008, with owner-account reconciliation); admin routes list, get, status, directory create, and ownership-history exist.
- **CON-008**: Verified Events/Documents baseline: Events has Create/Close/Get/List/`AdminSetCalloutStatus` but no update RPC, and callout responses live in Vendors (`callout_responses`). Documents has no upload RPC; its artifact tables hold generated documents (`owner_type` limited to `contract_revision`/`invoice`, constrained `object_key`).
- **PAT-001**: Follow `AGENTS.md`, `docs/frontend-ui-rules.md`, and existing TanStack Query and API-adapter patterns in `src/services/`.
- **PAT-002**: Implement workflow pages and domain components under focused files; do not expand `src/components/accounts/accounts-directory-pages.tsx` into the workflow implementation.

## 3. Alternatives

- **ALT-001**: Keep a single role per `(organization,user)` and infer permissions from the organization's full capability list. Rejected because a user cannot then hold distinct scopes or roles for multi-capability organizations, and `ResolveOrgPermissions` must match the requested scope.
- **ALT-002**: Keep sending legacy `type` and translate it implicitly in the UI. Rejected because the current gateway create contract requires `capabilities` and list filtering accepts `capability`; implicit translation hides contract drift.
- **ALT-003**: Use consumer-only KYB/member APIs with an admin token or impersonate the new owner. Rejected because those endpoints require consumer membership and impersonation would bypass identity/audit boundaries.
- **ALT-004**: Treat global venues or account-owned profiles as organization-owned by UI convention. Rejected because their owner-service records and authorization invariants differ.
- **ALT-005**: Hard-delete a callout on delete. Rejected because callout responses and lifecycle state require an auditable terminal state; cancel instead.

## 7. Risks & Assumptions

- **RISK-001**: Hard cutover means every caller of membership and permission lookups must change in the same release. Mitigate with the TASK-003 caller inventory and required scope fields so any unscoped call fails at compile time or in tests.
- **RISK-002**: Admin-assisted KYB could weaken evidence provenance if it accepts arbitrary URLs. Mitigate by accepting only Documents-owned artifact references and auditing actor, capability, and artifact IDs.
- **RISK-003**: Legacy organization filters are used by event, commerce, contract, marketplace, and callout pages. Mitigate by inventorying every caller and migrating them together with the API client type.
- **RISK-004**: Multi-step onboarding can leave a user or organization created when KYB submission fails. Mitigate with server-backed resumability and safe retry semantics; never repeat non-idempotent creates blindly.
- **RISK-005**: Vendor and venue records have existing account-owned, directory, claim, profile, service-area, derived-stat, and contract lifecycles. Mitigate by adding org-specific service methods and preserving existing workflows; never write derived ProfileStats from the admin client.
- **RISK-006**: Live admin validation can create durable records or expose KYB data. Mitigate by restricting it to a non-production disposable environment and sanitizing/removing test artifacts.
- **RISK-007**: Creating one owner membership per configured capability expands the owner's scoped membership rows. Mitigate by confirming the organization owner is the intended authority for every configured capability, reviewing the role mapping, and testing that no non-owner memberships or permissions are broadened.
- **ASSUMPTION-001**: Capability-to-scope mapping is fixed: `organize`→`organizer`, `vend`→`vendor`, and `host`→`venue`.
- **ASSUMPTION-002**: Each membership has one role in one scope; a member with multiple scopes has multiple membership rows keyed by `(org_id,user_id,scope)`.
- **ASSUMPTION-003**: Admin-assisted organization KYB is required because the requested workflow is performed in Admin; it must have separate authorization and audit attribution from consumer submission.
- **ASSUMPTION-004**: Organization profile/venue delete actions archive or deactivate records referenced by bookings/contracts; physical deletion is reserved for unreferenced drafts if owner services explicitly allow it.
- **ASSUMPTION-005**: Vendor callout lifecycle uses close/cancel rather than hard delete; edits are allowed only while the callout remains open.
